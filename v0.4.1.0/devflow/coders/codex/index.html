coder: codex¶

衍生值對照表，只有通用節（值欄宣稱可重用的工具能力或程序，repo 與環境只是可替換的參數）。本機節——具名的環境 instance——住 devflow.local/<同路徑>，不隨 kit 安裝。分節與狀態欄依 R9。

權限 — --sandbox read-only|workspace-write 的隔離依賴 host 能建 user namespace（Codex 的 Linux 沙箱用 bubblewrap 實作）；建不起來時 Codex 不拒絕執行、也不停下診斷，而是印 warning: Codex's Linux sandbox uses bubblewrap and needs access to create user namespaces. 後照跑，等同 danger-full-access；workspace-write 模式連這行 warning 都不印，靜默無隔離。host 能建 user namespace 時隔離成立：read-only 下 workdir 內外的寫入皆被 Read-only file system 拒；workspace-write 的可寫根預設是 workdir ＋ /tmp ＋ $TMPDIR，不是只有 workdir（codex exec 開頭的 header 會印 sandbox: workspace-write [workdir, /tmp, $TMPDIR]），可寫根外的寫入被拒 ✅ 可用（驗證方式：先在 host 上跑 bwrap --unshare-user --bind / / true 確認 host 條件，失敗則本格前提不成立、以下結果不會重現。再對乾淨 /tmp clone 執行 codex exec -C <clone> --sandbox read-only -o <out> - < <probe.txt>，probe prompt 依序要求 (1) 讀一個檔 (2) 跑 git log (3) 寫 clone 外的 /tmp/ro-probe-out.txt（此路徑須與 <probe.txt> 不同——同路徑會自撞，檔案必然存在，判不出有沒有落地） (4) 寫 clone 內一檔，並對 (3)(4) 各跑一次 ls -l 回報；隔離成立則 (3)(4) 皆被拒、兩檔皆不存在。workspace-write 再跑一次：因 /tmp 在該模式下本來就可寫，(3) 要改成寫可寫根外的路徑（例如 $HOME 下的一個檔）才測得到邊界，預期 (3) 拒、(4) 成功。判落地一律由派工者自己 ls／讀檔確認，不採信模型回報。實跑：orchestrator 於 332ab9d 首次跑，四步全 ok，/tmp/ro106-probe.txt 與 /tmp/ro106/PROBE.md 皆真的落地——隔離不成立；同一 host 直接跑 bwrap 即失敗：setting up uid map: Permission denied／loopback: Failed RTM_NEWADDR: Operation not permitted，故該 host 上兩模式皆無隔離。根因與修法：Ubuntu 24.04 的 kernel.apparmor_restrict_unprivileged_userns=1 擋掉沒有 AppArmor profile 的 bwrap；裝 /etc/apparmor.d/bwrap（flags=(unconfined) ＋ userns 授權，只給 bwrap 一個 profile 名字，沿 Ubuntu lxc-usernsexec 的模式）後 bwrap --unshare-user --bind / / true 成功。修復後於 b9f985a 的 /tmp/ro127 clone 重跑：read-only 的 (1)(2) ok、(3)(4) 皆 /bin/bash: …: Read-only file system，派工者自查 <probe.txt> 內容原封未被覆寫、clone 內 PROBE.md 不存在；workspace-write 的 clone 內 PROBE.md 與 /tmp 下的檔皆寫成（兩者都在可寫根內），改寫 $HOME 下的路徑則 Read-only file system 且檔案不存在——兩模式邊界皆與值欄相符。受測環境（R10）——首次驗證：2026-09-20，codex-cli 0.149.1、bwrap 0.9.0（該次為負結果）；最近確認：2026-09-21，codex-cli 0.149.1、bwrap 0.9.0，coder session 2a538534。兩次共同條件：模型 gpt-5.6-sol／reasoning low；執行身分為本機使用者以 Codex 訂閱登入；目標 repo AugustusHsu/agent-devflow 的 /tmp clone。host 條件：bwrap --unshare-user --bind / / true 須成功——這是本格成立的前提，host 的 AppArmor／kernel.apparmor_restrict_unprivileged_userns／userns 相關設定變更使該條件不再成立時，本格依 R10 降為 📝。證據：https://github.com/AugustusHsu/agent-devflow/issues/127#issuecomment-5751267413 ；負結果原始紀錄 https://github.com/AugustusHsu/agent-devflow/issues/106#issuecomment-5748372216）
worktree（I2） coordinator（建）／implementer（不自建） 由 orchestrator 建 📝 已宣稱（R9 子類「驗證未達 ✅」：本格附有第三者現在能執行的驗證方式，實跑結果與值欄宣稱相符，但不滿足 ✅ 的成立條件，理由見末段。驗證方式：orchestrator 先以 git worktree add 建好 worktree，coder 以 codex exec -C <該路徑> 進入；事後 grep 該次 --json 事件流裡的全部指令，git worktree、git checkout -b、git switch 三者皆無命中，即 coder 未自建 worktree 或分支。實跑：#110 派工的 18 個指令中三者皆 0 命中，Codex 全程在 orchestrator 預建的 worktree 內工作。受測環境：2026-09-20，codex-cli 0.149.1、模型 gpt-5.6-sol／reasoning high；執行身分為本機使用者以 Codex 訂閱登入；目標 repo AugustusHsu/agent-devflow，worktree agent-devflow.worktrees/110。為何不是 ✅：驗證由 orchestrator 執行並回報，尚無第三者獨立重跑。證據：https://github.com/AugustusHsu/agent-devflow/issues/110#issuecomment-5748564171）
HITL（L3） implementer headless 無互動 → issue 留言後停 ⬜ 未測（2026-09-20 嘗試驗證（#110）：派工 prompt 未明令「留言後停」，只指向 L3 原文；coder 讀了 L3（事件流引用 23 次）、讀了三張 PR 的紀錄，自判「比對結果已足以收斂」後直接改，未留言。本任務的未決事項強度不足以區分「判斷不需停」與「不會停」——它的判斷可能是對的。需未決事項更明確（處置明顯落在 write scope 外、或 G／T 明顯衝突）的載體才能驗，見 https://github.com/AugustusHsu/agent-devflow/issues/110#issuecomment-5748564171）
審查用法（R1） reviewer 於乾淨 checkout 執行 codex exec -m <model> -c model_reasoning_effort=<level> --sandbox workspace-write -o <verdict.md> - < <prompt.txt>；末尾的 - 表 prompt 由 stdin 餵入。checkout 以 git clone --shared 到 /tmp 後 git checkout <head sha>。--shared clone 的 origin 是本機路徑，gh 無法自動推導 repo（錯誤：none of the git remotes … point to a known GitHub host）——須 git remote set-url origin 成 GitHub remote（HTTPS 或 SSH），或以 gh --repo <owner/repo>／GH_REPO 明示。--skip-git-repo-check 在此非必要：它只放行「非 git 目錄」（在非 git 目錄不加它會擋：Not inside a trusted directory and --skip-git-repo-check was not specified），而 /tmp checkout 本身是 git repo 📝 已宣稱（有可執行的驗證方式：本 repo #80→#105 的 Codex 審查全以此形式實跑，verdict 貼於各 PR；來源 orchestrator（Hermes）。R9 子類「驗證未達 ✅」——受測環境記載與第三者重跑證據待 #106 第二輪補齊後再判能否升 ✅。原值欄並列的 codex exec review 依 R7 拆成下一列）
審查用法：review 子命令（R1） reviewer codex exec review——Codex 內建的 code review 子命令 ⬜ 未測（子命令存在已驗：codex exec --help 於 codex-cli 0.149.1 列出 review Run a code review against the current repository。但未驗證它能否讀自訂 review prompt、能否輸出到指定檔；本 repo 至 332ab9d 止從未用過。依 R7 與上一列拆開各自標狀態，不共格，見 #106 AC-1）
