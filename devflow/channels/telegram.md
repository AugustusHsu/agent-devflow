## 已知限制（文件推導，待實測）

- Bot API 無列出 forum topic 的方法；issue 與 topic 的對應須自行維護，forge 上的記載為權威（`README.md` 職能 4）。
- 「seat 間喚醒」、「在 General 下指令的限制」、「session 與 thread 的綁定」三個 `✅` 格的驗證方式都需要第三者自備 Telegram forum group 與 ≥2 個 bot；「封存程序」格需要一個 administrator 權限的 bot 與自建的誘餌分區（**不得拿真實單的分區當靶**，`deleteForumTopic` 不可逆）；「分區狀態判準」格的 (1)(3)(4)(5) 與「封存標記寫入」格（`✅`）的 (1)(3) 只需 `gh` 與該 repo 的讀權，該格的 (2) 另需 issue 編輯權與一個可丟棄的誘餌分區；「封存標記 upsert 反測」格要重跑一次 `archive`，需 issue 編輯權加一張已封存的真實單或自建的誘餌分區；「分區狀態 INVALID 判定」格全部以自造的 body fixture 驗，只需 `gh` 讀權與一個編輯器，不需 Telegram 權限。無此環境者只能依 `R9` 當 `📝`／`⬜` 引用。
- 凡要被 parse mode 解析的文字，插入外部字串前一律轉義，**不分人工或程式產生**（`#291` 封存時 issue 標題的裸底線、人工貼 MarkdownV2 字元清單時的裸反引號，同一個病）。
- **`CH3` 生效前封存的單 `A=0` 屬既有狀態，不視為 INVALID，也不回頭補寫**：判準以 `CH3` 生效的 commit `47868ca`（2026-10-04 23:45:14，`#283` 合併、kit 0.15.0.0）為界——在它**之前**封存的單，當時封存標記尚未定義，body 讀回 `T=1 A=0` 是**既有狀態**，依 `README.md` 「分區三態」照 active 判讀即可，不觸發 INVALID 分支（INVALID 的四類組合是 `T=0 A=1`／`T>1`／`A>1`／`NN` 不符，`A=0` 不在其中）。名單五張，forge 實查皆 `T=1 A=0`：`#258`／`#272`／`#275`／`#277`／`#279`。**不補的理由**：補寫要人工填 `file=`，那會讓這五張單的 body 出現一次沒有實質根據的修改（封存當時沒有程式寫入的那一行，事後補出來的值無從由當次封存的紀錄佐證）；它們的匯出檔都在 `~/.hermes/archives/topics/` 可查，封存事實不因 body 缺一行而消失。同理，`C5` 第一項改為「該單的專屬子目錄不存在」之後，**既有暫存根裡的歷史散檔不在該判準的射程、不清理**（那裡有他單的產物與 runtime 的活體資源，`C3`）——新判準只約束其後各單自己的專屬子目錄，不得讀成「收尾要清空整個暫存根」。
