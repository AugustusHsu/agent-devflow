# devflow/channels — 通道層

kit 的第五層。`forges/` 定工作產物住哪、`orchestrators/` 定誰驅動流程、`coders/` 定用什麼工具實作、`seats/` 定職位；**本層定 seat 與人之間的對話介面住哪**。由 `devflow.yml` 的頂層鍵 `channel` 選用（值域 `none | telegram`，省略＝`none`），每個值對應本目錄一個說明檔：`none.md`、`telegram.md`。規則本體在 `WORKFLOW.md` 第 13 節（`CH1`、`CH2`、`CH3`），行為人是協調位（`seats/coordinator.md`）。

## 四職能

通道只承載下列四件事，其餘（工單、證據、裁決、合併）都不在這一層：

1. **出站通知**：流程要人知道的事往通道推——升人（`R13` `E1`～`E3`）、擱置、`L3` 提問、里程碑（PR 開出、每輪 verdict、合併、收尾）。
2. **入站裁決**：人在通道上回覆。回覆本身不是裁決——依 `CH1`，協調位把它寫回 forge（issue 或 PR 留言）後才成立。
3. **seat 身分投影**：每個 seat 在通道上各有一個可辨識的身分（Telegram 為每 seat 一個 bot），同一對話內的訊息能分辨來自哪個職位；`launch: agent` 的填充者每個工具呼叫由協調平台投影到通道（`orchestrators/hermes/SKILL.md` 第二節），載體與格式由本層的對照表定。
4. **對話分區**：一張 issue／PR 對應通道上一個分區（Telegram 為 forum topic）；分區與 issue 的對應以 forge 上的記載為準，不以通道側的快取為準。

## 核心條款：forge 是唯一權威（`CH1`）

通道訊息不構成裁決。流程必須是「通道收到人的回覆 → 協調位寫回 forge → 才算成立」。理由：`R5`（審查證據住 forge）與 `L3`（答案寫回 issue，提問通道只是通道）已是現行規則；若裁決只存在於通道，下一輪的審查位（`R1` fresh context）讀不到——那是懸空引用的制度化版本。本條把兩條既有規則對通道的含意寫成一條，不新增 forge 以外的權威來源。

## 通道故障分級（`CH2`）

| 通知類別 | 送達失敗時 |
|---|---|
| 須由人裁決的通知（升人、擱置、`L3` 提問） | **阻塞**：協調位停下，在 forge 留言記錄「通知失敗」，等人讀到 |
| 其他通知（流程播報、verdict 摘要、里程碑） | 只記 log，流程照跑 |

分界理由（`#258` 2026-09-27 裁示 Q5(c)）：一律照跑會讓「需要人裁決」的單靜默卡住；一律阻塞會讓通道故障癱瘓整條流程。通知只是提醒，但提醒失敗時人必須知道。

## 為什麼這層會有實作

其他四層全是 `.md` 對照表；本層另容納 `scripts/<channel>/` 下的 `.py` 參考實作，理由與邊界：

- **理由**：通道的操作（建分區、投影事件流、封存）綁定平台 API 與協調平台的事件格式，無法只靠對照表描述讓第三者照做；對照表宣稱的能力需要可執行的參考實作才能依 `R8` 驗。
- **位置**：`devflow/channels/scripts/<channel>/`，而非 repo 根 `scripts/`。`devflow/install.py` 的擁有權表只鏡像 `devflow/**`——放根目錄的話消費者裝了 kit 卻沒有腳本，等於沒納管。
- **邊界**：子目錄以平台命名（`scripts/telegram/`），內容是**該通道的參考實作，非通用**；換平台的消費者不拿它跑，照對照表另寫。腳本本身不是規範，`I7` 對它同樣適用：只能收窄或細化 `devflow.yml` 與 `WORKFLOW.md`。
- **本單狀態**：目錄已建、腳本未搬（`scripts/telegram/README.md`）；搬入與缺陷修正屬 K4c。

## 通道側收尾（`C5`、`CH3`）

單結束時通道側也有收尾：**該單的分區要封存**。這是 `C5` 的一項，不是收尾之外的附加動作——**分區未封存即收尾未完成**，不得回報完成（補做依 `F4`）。本節定分區封存與分區狀態；本機工作檔的收斂不在本層（`profile`、暫存目錄是協調平台的概念，換 orchestrator 就沒有，依 `I6` 歸 `orchestrators/`）。

條文層的義務在 `WORKFLOW.md` 的 `C5` 與 `CH3`；各平台的封存步驟與留痕形狀在本目錄的對照表（`telegram.md`、`none.md`）。`channel` 為 `none` 時通道側無分區可封存，該項自動滿足。

### 分區三態

分區只有三態。**權威一律在 issue body 的機器可讀標記**（`CH3`、職能 4）。兩個標記各有唯一字面，都是**獨立一行**的 HTML 註解（與 `devflow_topic.py` 既有的寫法同族——該檔把標記以獨立行 append 到 body 末，見 `:78-80`）：

```
<!-- devflow:topic thread=NN -->                              分區標記（既有）
<!-- devflow:archived thread=NN file=<匯出檔路徑或 URL> -->    封存標記（本層定義）
```

`NN` 為十進位 thread id；`file=` 記載匯出檔位置（`<路徑或 URL>`，不含空白與 `>`），這是封存的實體所在，`CH3` 要求的「記載匯出檔位置」即此欄。兩個標記的 `NN` 須相同。

| 態 | 機械判準（權威一律在 issue body） | 判定式（`B=$(gh issue view <N> --json body --jq .body)`） |
|---|---|---|
| 未開始 | 無分區標記，**且**無封存標記 | `T=0` **且** `A=0` |
| active | 恰一個分區標記，且**無**封存標記 | `T=1` 且 `A=0` |
| 已封存 | 恰一個分區標記，**且**恰一個合法封存標記、兩者 `NN` 相同 | `T=1` 且 `A=1` 且 `NN` 相同 |

其中 `T=$(printf '%s\n' "$B" | grep -cE '^<!-- devflow:topic thread=[0-9]+ -->$')`、`A=$(printf '%s\n' "$B" | grep -cE '^<!-- devflow:archived thread=[0-9]+ file=[^ >]+ -->$')`。

**其他組合（含 `T=0 A=1`、`T>1`、`A>1`、`T=1 A=1` 而 `NN` 不符）＝INVALID，須人工處置，不得視為任一態。** 三個成功態**彼此互斥**（任一組 `(T, A, NN)` 最多命中一個）；三個成功態**加上 INVALID 這個 catch-all**，才對所有標記組合互斥且窮盡——INVALID 不是第四個態，是「不落在三態」的收容分支，所以成功態那邊不留「其餘歸某一態」的缺口：`T=0 A=1`（有封存標記而無分區標記）若落進「未開始」，該單會被重建分區、覆寫既有匯出檔——這正是 `CH3` 要防的那件事（`#279` 的實例）；`T>1`／`A>1`（重複標記）表示標記被手動加過或 upsert 失敗，兩行的 `NN` 可能不同，此時「該單的分區是哪一個」沒有單一答案，同樣只能停。判定程式須對 INVALID 回非 0 或明確吐 `INVALID`，不得靜默取其一。
三態判定只讀分區狀態標記（`devflow:topic`／`devflow:archived`）：其他 `devflow:*` 標記（例如轉播器寫的 handoff 行）不參與三態判定，判定式各自錨定完整字面，不計其他行。

判定式三條都錨行首行尾（`^…$`）。這不是風格——**標記必須是獨立一行才算**：寫在表格列裡（行首是 `|`）、寫成旁註或散文的一部分、或字面近似而不合 grammar（缺 `file=`、`thread=` 非數字、`file=` 含空白、改用 `devflow:archive`／`devflow:topic-archived` 等別名）都不使 `A` 增加，故有分區標記者**維持 active**，不會被誤判為已封存。本層的判準刻意只認一種字面：封存是不可逆動作（刪分區），判準寬鬆的代價是把「其實還開著」讀成「已封存」。

兩件事由此得到保證：

- **已封存與未開始機械可區分**，差別是有沒有 `<!-- devflow:archived … -->` 標記。封存會刪掉平台上的分區、也會清掉本機快取，若不另留封存標記，從未建分區的單與已封存的單在通道側與快取皆為空——`#279` 即因此被重做封存、覆寫原始匯出檔。封存標記使該單**不回到無標記的狀態**，且 `file=` 欄指出匯出檔，重做封存前能先看到已經有一份。
- **本機快取不是權威**。它會殘留已刪除的分區（`#251` 的 `state` 欄即錯過一次），也會在封存的最後一步被清掉；它只是加速用的，判定態一律回 issue body 讀。平台側同樣不是權威：Bot API 無列出分區的方法（`telegram.md`），分區與 issue 的對應一旦只存在於通道側就無法重建。

### 為什麼不是四態

原定的第四態「關閉」沒有機械判準，三項實測如下：Bot API 無 `getForumTopic`；`sendMessage` 測不到（bot 是 administrator，關閉中的分區也能發）；本機快取的 `state` 欄在 `#251` 已錯過一次。關閉只是封存程序的中間步驟（先停止寫入、再移除），不是需要外部判定的態——所以它不入三態。

## 人格檔範本（`templates/`）

本目錄另有 `templates/`：四份 seat 人格檔的**通道側操作規範**範本，各自對應 `seats/` 下
同名的職位檔。它承載的是「在通道上怎麼做」——分區界線、確認節點、里程碑播報、轉播器
用法、封存程序、唯讀執行的註明、session 累積與全新的分界、工具呼叫的可見性。

與 `seats/` 的分工：**`seats/` 是職位本體**（職責、產出物、禁止、context 語意、規則義務，
不綁工具）；**`templates/` 是人格檔範本**，只寫通道側的操作形式，職位本體一律引用
`seats/` 不複製（`I5`）。範本凡述及規則處寫規則 ID ＋ 一句摘述、凡述及通道側操作形式則
引用 `telegram.md` 的格名或本檔的節名，都不抄原文。

範本是什麼、怎麼用、占位符清單、為何不由安裝產生、共用句的抽出門檻、以及 (c) 的已知
上限，全住 `templates/README.md`——本節只指路，不複製（`I5`）。

放在通道層而非 kit 的通用範本目錄，理由同上節「為什麼這層會有實作」：正確性隨 `channel`
的值而變，`channel` 為 `none` 的專案不需要這些範本。

- bot 替換、環境結帳：K4d。人格檔範本已納入本層（`templates/`，見上節）。
