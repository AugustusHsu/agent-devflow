# devflow/channels — 通道層

kit 的第五層。`forges/` 定工作產物住哪、`orchestrators/` 定誰驅動流程、`coders/` 定用什麼工具實作、`seats/` 定職位；**本層定 seat 與人之間的對話介面住哪**。由 `devflow.yml` 的頂層鍵 `channel` 選用（值域 `none | telegram`，省略＝`none`），每個值對應本目錄一張對照表：`none.md`、`telegram.md`。規則本體在 `WORKFLOW.md` 第 13 節（`CH1`、`CH2`），行為人是協調位（`seats/coordinator.md`）。

## 四職能

通道只承載下列四件事，其餘（工單、證據、裁決、合併）都不在這一層：

1. **出站通知**：流程要人知道的事往通道推——升人（`R13` `E1`～`E3`）、擱置、`L3` 提問、里程碑（PR 開出、每輪 verdict、合併、收尾）。
2. **入站裁決**：人在通道上回覆。回覆本身不是裁決——依 `CH1`，協調位把它寫回 forge（issue 或 PR 留言）後才成立。
3. **seat 身分投影**：每個 seat 在通道上各有一個可辨識的身分（Telegram 為每 seat 一個 bot），同一對話內的訊息能分辨來自哪個職位；`launch: agent` 的填充者每個工具呼叫由協調平台投影到通道（`orchestrators/hermes/SKILL.md` 第二節），載體與格式由本層的對照表定。
4. **對話分區**：一張 issue／PR 對應通道上一個分區（Telegram 為 forum topic）；分區與 issue 的對應以 forge 上的記載為準，不以通道側的快取為準。

## 核心條款：forge 是唯一權威（`CH1`）

通道訊息不構成裁決。流程必須是「通道收到人的回覆 → 協調位寫回 forge → 才算成立」。理由：`R5`（審查證據住 forge）與 `L3`（答案寫回 issue，提問通道只是通道）已是現行規則；若裁決只存在於通道，下一輪的審查位（`R1` fresh context）讀不到——那是懸空引用的制度化版本。本條把兩條既有規則對通道的含意寫成一條，不新增 forge 以外的權威來源。

## 通道故障分級（`CH2`）

| 通知類別 | 送達失敗時 |
|---|---|
| 須由人裁決的通知（升人、擱置、`L3` 提問） | **阻塞**：協調位停下，在 forge 留言記錄「通知失敗」，等人讀到 |
| 其他通知（流程播報、verdict 摘要、里程碑） | 只記 log，流程照跑 |

分界理由（`#258` 2026-09-27 裁示 Q5(c)）：一律照跑會讓「需要人裁決」的單靜默卡住；一律阻塞會讓通道故障癱瘓整條流程。通知只是提醒，但提醒失敗時人必須知道。

## 為什麼這層會有實作

其他四層全是 `.md` 對照表；本層另容納 `scripts/<channel>/` 下的 `.py` 參考實作，理由與邊界：

- **理由**：通道的操作（建分區、投影事件流、封存）綁定平台 API 與協調平台的事件格式，無法只靠對照表描述讓第三者照做；對照表宣稱的能力需要可執行的參考實作才能依 `R8` 驗。
- **位置**：`devflow/channels/scripts/<channel>/`，而非 repo 根 `scripts/`。`devflow/install.py` 的擁有權表只鏡像 `devflow/**`——放根目錄的話消費者裝了 kit 卻沒有腳本，等於沒納管。
- **邊界**：子目錄以平台命名（`scripts/telegram/`），內容是**該通道的參考實作，非通用**；換平台的消費者不拿它跑，照對照表另寫。腳本本身不是規範，`I7` 對它同樣適用：只能收窄或細化 `devflow.yml` 與 `WORKFLOW.md`。
- **本單狀態**：目錄已建、腳本未搬（`scripts/telegram/README.md`）；搬入與缺陷修正屬 K4c。

## 本層不管的事

- 單結束時通道側的收尾（分區封存、狀態機）：K4b。
- 腳本與其缺陷：K4c。
- bot 替換、環境結帳、人格檔範本：K4d。
