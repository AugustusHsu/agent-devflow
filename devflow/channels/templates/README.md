# devflow/channels/templates — 人格檔範本

## 這些範本是什麼

四份 seat 人格檔的**通道側操作規範**範本，各自對應 `devflow/seats/` 下同名的職位檔：

| 範本 | 對應職位檔 |
|---|---|
| `coordinator.md` | `devflow/seats/` 的 `coordinator.md` |
| `manager.md` | `devflow/seats/` 的 `manager.md` |
| `reviewer.md` | `devflow/seats/` 的 `reviewer.md` |
| `implementer.md` | `devflow/seats/` 的 `implementer.md` |

人格檔是填充者的操作層設定，`I7` 對它的定位是只能收窄或細化規則本體與 `devflow.yml`、
不得牴觸。四份範本因此都以同一行開頭宣告這件事，且**凡述及規則處一律寫規則 ID ＋ 一句
摘述，不抄條文原文**——抄進來的那一刻就會與規則本體各自演化。

職位本體（職責、產出物、禁止、context 語意、規則義務）住 `devflow/seats/`，範本不複製
（`I5`：一個事實只住一處）。範本只承載「在通道上怎麼做」：分區界線、確認節點、里程碑
播報、轉播器用法、封存程序、唯讀執行的註明、session 累積與全新的分界、工具呼叫的可見性。

通道側的操作形式同樣不複製：範本一律引用 `telegram.md` 的格名或 `channels/README.md` 的
節名，值與證據留在對照表那一格。本目錄住在通道層而非 kit 的通用範本目錄，理由與
channels/README.md「為什麼這層會有實作」那節同一個——正確性隨 `channel` 的值而變，
`channel` 不走通道的專案不需要這些範本。

## 怎麼用

1. 挑對應你的 seat 的那一份，**複製**進你自己協調平台的人格檔位置（Hermes 為 profile
   目錄下的 `SOUL.md`，其他平台查該平台文件）
2. 把占位符換成你的實值
3. 加上你自己環境的本機內容（具名 instance、路徑、模型選擇、該環境的已知陷阱）——
   那些刻意**不在**範本裡，見下方「範本不含什麼」

占位符一覽（四份共用同一組寫法）：

| 占位符 | 填什麼 |
|---|---|
| `<scripts-dir>` | 通道腳本所在目錄 |
| `<thread>` | 該單在通道上的分區 id |
| `<N>` / `<M>` | issue 號 / PR 號 |
| `<repo>` | forge 上的 repo 識別（`<owner>/<name>`） |
| `<home>` | 執行身分的家目錄 |
| `<worktree-root>` | 放任務 worktree 的目錄 |
| `<channel-target>` | 送訊息的目標位址 |
| `<send-cmd>` | 協調平台的送訊指令 |
| `<本 seat 的 profile>`、`<實作位 profile>`、`<審查位 profile>` | 各 seat 在協調平台上的 profile 名 |

## 範本不由安裝產生（刻意，不是遺漏）

`devflow/install.py` 整樹鏡像 `devflow/`，所以本目錄會隨安裝出現在消費者 repo 裡；
但**它不會把範本寫進你的人格檔位置**，那一步要你自己做。

這是刻意的。人格檔的目標位置是**協調平台的設定**，而 `I6` 要求換掉 orchestrator 工具時
forge 與 coder 那兩側的行為不受影響——讓 kit 伸手去寫協調平台的設定正好是反方向。故
`install.py` 不在本單的射程內，範本只是鏡像進來的檔案，由使用者自行取用。

## 範本不含什麼

| 不含 | 理由 |
|---|---|
| 本機具名 instance（使用者名、群組 id、絕對路徑） | 它們是環境參數，不是可重用的規範；一律以占位符表達 |
| 本 repo 的經驗史（事故編號、實跑紀錄） | 範本是給別人用的，夾帶本 repo 的特例只會誤導 |
| 規則本體的條文原文 | 引用 ID ＋ 摘述即可；抄原文就會漂移 |
| 協調平台注入的 persona 前言 | 見下節 |

### persona 前言不進範本是機械事實，不是偏好

Hermes 在每個 session 的第一行注入一段 persona 前言（以「You are Hermes」開頭的那一句）。
那一行**不是人格檔的內容**，而是 **runtime 注入**的：四份人格檔的第 1 行逐字相同，連
沒有任何 devflow 內容的 default profile 也有同一行。

所以把它抽進範本有兩個後果：違 `I6`（換掉協調平台之後那段話毫無意義），以及讓範本與
runtime 的注入打架（同一段文字出現兩次）。這是**機械事實**——可由「四份第 1 行相同 ＋
default profile 亦有」直接讀出，不是誰的風格判斷。

## 共用句與抽出門檻

四份範本有一行逐字相同：

```
**本檔只能收窄或細化 `devflow/seats/**` 與 `devflow/WORKFLOW.md`，不得牴觸。**
```

它**逐字重複四次**，刻意不抽成共用檔。單行句的漂移風險接近零，重複的成本低於多一個檔案
與一層引用的成本。

**若將來四份範本的逐字共同行增至 3 行以上，重新評估抽出共用檔。**

判準是**逐字相同**，不是意思相近。這個限定是必要的：`#285` 的 marker grammar 五份拷貝
正是「為消除重複而把幾個不完全相同的東西塞進一個模板」的形狀，用「意思相近」當邊界會
重演它。四份的「效力層級」節除了上面那一行之外各自寫法不同，那些差異很可能有理由
（例如只有協調位會收到條文衝突的回報），本層不動它們。

## ⚠️ (c) 的已知上限

**範本引用條文只保證「範本不漂移」，不保證「使用者照範本做」。**

- 範本是 kit 內的檔案 → **進入 AC 的視野**（可被本單與後續單的 AC 驗）
- 實際的人格檔仍住 profile 目錄 → **仍在 AC 視野外**

即本單**只解決來源側**：kit 提供了不漂移的來源，但「profile 與該來源是否同步」無人檢查。
**該缺口留給 K6。** 本層因此不含任何檢查 profile 的機制——那會讓 kit 伸手管協調平台的
設定，與上方「不由安裝產生」同一個理由。
