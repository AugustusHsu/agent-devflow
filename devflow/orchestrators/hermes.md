# orchestrator: hermes

Hermes Agent 當協調者：確認範圍、固定 G／T、建 worktree、啟動 coder、向人提問、驗證交付、收尾。

| 面向 | 值 | 狀態 |
|---|---|---|
| 派工（`L2`） | 用 `terminal` 直接啟動 coder CLI（見 `coders/`），保存程序或 session 識別。本派工路徑**不使用 `delegate_task`** | ✅ 實測 2026-09-11（驗證方式：在 orchestrator 的頂層 session 以 `terminal(command="cd <worktree> && systemd-run --user --scope --unit=coder-<N> --collect -q <coders/ 表上的 CLI 指令> > <stdout 檔> 2> <stderr 檔> < /dev/null", background=true)` 啟動 coder（`systemd-run --scope` 把 coder 及其所有子孫放進專用 cgroup，`--unit` 名稱是中斷交接格的中斷把手；無 systemd 的平台另找監督邊界），記下該工具回傳的 pid；再於同一台機器讀回三項——(1) `pstree -p <該 pid> \| head -1` 的鏈上出現 `claude(<coder pid>)`；(2) `tr '\0' ' ' < /proc/<coder pid>/cmdline` 以 `claude -p` 開頭；(3) `readlink /proc/<coder pid>/cwd` 等於該 worktree 路徑。第 (1) 項連同完整的 `terminal` 呼叫紀錄，證明本次 coder 是由 `terminal` 啟動的外部進程；「不用 `delegate_task`」由呼叫紀錄判定（紀錄中無 `delegate_task` 呼叫），本格**不宣稱** `delegate_task` 的進程樹長什麼樣——那未實測。值欄「保存程序或 session 識別」兩項分別由 `terminal(background=true)` 回傳、稍後仍可用來讀回該進程的 pid，與 stdout 檔內 JSON 的 `session_id`（見 `coders/claude-code.md` 的 headless 執行格）判定。**不要用 `ps -eo pid,args \| grep 'claude -p'`**：coder 的 prompt 為多行時 `ps` 的 args 顯示不可靠，會讀到空結果而誤判進程不存在。此程序不依賴本次的 prompt 或 repo，第三者現在可獨立重跑。受測環境：2026-09-11；orchestrator 為 Hermes Agent v0.21.1（2026.9.7），coder 為 Claude Code 2.1.267 headless；程序讀回依賴 Linux 的 `/proc` 與 `pstree`（無 `/proc` 的平台須另找讀回方式）；執行身分為本機 OS 使用者，與 coder 進程同 UID；`readlink /proc/<pid>/cwd` 受 `PTRACE_MODE_READ_FSCREDS` 檢查（`proc_pid_cwd(5)`；同 UID 但目標 `PR_SET_DUMPABLE=0` 時讀取失敗），`/proc/<pid>/cmdline` 不受該檢查；本次在同 UID、預設 dumpable、無額外 LSM 限制的環境兩者皆讀取成功，其他環境（容器、不同 UID、Yama ptrace_scope）須自行確認；pstree (PSmisc) 23.7；目標 repo `AugustusHsu/agent-devflow`；證據：issue #33 留言 https://github.com/AugustusHsu/agent-devflow/issues/33#issuecomment-5624350935（完整 `terminal` 呼叫）＋ https://github.com/AugustusHsu/agent-devflow/issues/33#issuecomment-5624355903（進程樹與 `/proc` 讀回）） |
| 建 worktree（`I2`） | `git worktree add ../<repo>.worktrees/<N> <N>-<slug>` | ✅ 實測 2026-09-11（驗證方式同 `coders/claude-code.md` 的 worktree 格，主體換成 orchestrator：orchestrator 在主 checkout 以 `terminal` 執行 `git branch <N>-<slug> origin/main`，再執行 `git worktree add ../<repo>.worktrees/<N> <N>-<slug>`；啟動 coder 前以 `git worktree list` 確認輸出含該路徑與分支名，並以 `git -C ../<repo>.worktrees/<N> rev-parse HEAD` 確認該 worktree 的 HEAD 等於 base commit。判定點：worktree 路徑落在 repo 目錄之外（`I2`），主 checkout 那一列仍停在原分支與原 commit，且 coder 只收到該路徑。此程序不依賴本次的 issue 或 repo，第三者現在可獨立重跑。受測環境：2026-09-11；orchestrator 為 Hermes Agent v0.21.1（2026.9.7），以 `terminal` 工具執行本機 `git version 2.43.0` 的 `branch`／`worktree` 子命令；執行身分為對該 repo 工作目錄具寫入權限的本機 OS 使用者（本步驟不需 forge 權限）；目標 repo `AugustusHsu/agent-devflow`，base `origin/main @ 333d087`；證據：issue #33 留言 https://github.com/AugustusHsu/agent-devflow/issues/33#issuecomment-5624350935） |
| HITL（`L3`） | 向人提問，答案寫回 issue 留言（持久紀錄）；派工前未決事項為空 | ⬜ 未實測（值欄已依 `R7` 改寫：原文「`clarify` 問人」把工具名當機制，`L3` 明文「提問通道只是通道」。迴路「coder BLOCKED 留言 → 人類裁決留言（含依據）→ 重派」在 issue #4 確實走過（留言 5622863707 → 5623110580 → 5623153788），但那是**歷史紀錄**——第三者現在只能讀回、不能重新執行「提問 → 裁決 → 寫回 → 重派」，依 `R8` 屬追溯讀法，不足以 `✅`。升格需要第三者現在可主動重跑的演練：派工前 issue「未決事項」為空（`L1`），coder 執行中在 issue 留言提出未決事項並停下，orchestrator 向人提問、把裁決連同依據寫回同一 issue、再以 `--resume` 重派——本格判定的是 orchestrator 側這三步是否發生；coder 是否**自發**停下屬 `coders/claude-code.md` 的「HITL（`L3` 遵從）」格，可共用同一場演練但分別判定） |
| 平行上限 | 上限依 `stage`：stage 1–2 由 `ST` 定（`ST1`：同時只有一個任務），沒有可調的旋鈕；stage 3 起才由人設定，並依 `P1` 逐項確認寫進 issue（`P4`） | ⬜ 未實測（本單依 `R7` 改寫值欄，狀態不升。理由：原值欄「人設」在今日的 stage 1 不是實際生效的機制——`devflow.yml` 為 `stage: 1`，`ST1` 已把同時活躍任務定為 1，沒有人可設定的上限；`P1`／`P4` 住第 12 節，依 `ST3` 要 stage 3 才生效。本 issue 雖已填「平行前提」四欄（write scope、阻塞依賴、共用契約、外部資源），但那是 stage < 3 的預先累積：只有一張活躍任務時，`P1` 的判定（write scope 不重疊、共用契約無人同時改）無從被檢驗，依 `R8`（未執行的推測不構成 `✅`，且不得由「行為符合規則」反推機制已生效）不足以升格。待 stage 3 首次同時派兩張任務、由人實際設定上限並逐項確認 `P1` 時再測） |
| 流程指令住哪 | `devflow/orchestrators/hermes/SKILL.md`（尚未寫；依 Phase 2 實跑後萃取），接入方式待驗：symlink 進 `~/.hermes/skills/`、或 `skills.external_dirs`、或 trusted project-local skills | ⬜ 未實測 |
| skill 啟用邊界（`G3`） | skill 指向已核准版本，不指向編輯中的候選；驗證「載到正確內容與版本」，不只驗 symlink 存在 | ⬜ 未實測 |
| 中斷交接 | 保留 issue、分支、worktree、HEAD、未提交內容、最後可信驗證；確認舊 coder 已停才重派 | ✅ 實測 2026-09-11（驗證方式：在 coder 執行途中由 orchestrator 中斷（`kill` 該 coder 進程），中斷當下把值欄的六項保留物逐一讀回並貼成 issue 留言——(1) `gh issue view <N> --json state` 為 `OPEN`；(2) `git branch --list <N>-<slug>` 有該分支；(3) `git worktree list` 仍含該 worktree 路徑與分支；(4) `git -C <worktree> rev-parse HEAD` 的 sha；(5) `git -C <worktree> status --porcelain` 的未提交／未追蹤清單；(6) 中斷前最後一次驗證指令的原始輸出。再確認舊 coder 已停——coder 啟動時已放進專用 cgroup（見派工格的 `systemd-run --user --scope --unit=coder-<N>`），中斷用 `systemctl --user kill --signal=TERM coder-<N>.scope`（核心對 cgroup 當下全部成員送訊號），已停的判定是 `systemctl --user is-active coder-<N>.scope` 回 `inactive`、或 `$CG/cgroup.events` 的 `populated 0`（`CG=$(find /sys/fs/cgroup/user.slice -type d -name 'coder-<N>.scope')`）。cgroup 成員資格由核心維護、fork 出的子孫自動繼承，不需要 PID 快照，因此沒有「快照後 fork」或「reparent 後 `pgrep -P` 漏看」的 TOCTOU 缺口（兩者皆在審查中以反例實證過，單次 PID 快照＋逐一 `kill -0` 不足）——確認後才以 `--resume <session_id>` 重派，重派 prompt 告知「你被中斷過，先讀工作區狀態」。判定點三項皆須成立：重派後的 coder 讀到的 HEAD 與未提交內容和 (4)(5) 逐字相同；同一 worktree 沒有第二個 coder 進程；重派 stdout 的 `session_id` 與被中斷那段相同（見 `coders/claude-code.md` 的 `--resume` 交接格）。此程序不依賴本次的 issue 或 prompt，第三者現在可對任一 headless coder 重跑。受測環境：2026-09-11；orchestrator 為 Hermes Agent v0.21.1（2026.9.7），coder 為 Claude Code 2.1.267 headless（`--resume` 需被中斷段的 `session_id`；被 SIGTERM 的 headless session **不會**輸出 JSON，須從 `~/.claude/projects/<cwd 路徑編碼>/` 取最新 `.jsonl` 檔名，首行 `sessionId` 即是），git 2.43.0，gh 2.97.0；監督邊界為 systemd 255（255.4-1ubuntu8.17）user session 的 transient scope，cgroup v2；不需 root）；執行身分為本機 OS 使用者，須與 coder 進程同一使用者（`kill` 需要），且重派須由**同一 OS 使用者**執行（`--resume` 讀該使用者 `~/.claude/` 下的 session 紀錄，換身分即無法續接），並具 `AugustusHsu/agent-devflow` 的 `gh` 留言權限；目標 repo `AugustusHsu/agent-devflow`；證據：issue #33 cgroup 已停判定重測 https://github.com/AugustusHsu/agent-devflow/issues/33#issuecomment-5624794146 ＋ 中斷時狀態留言 https://github.com/AugustusHsu/agent-devflow/issues/33#issuecomment-5624437437 ＋ https://github.com/AugustusHsu/agent-devflow/issues/33#issuecomment-5624479141） |

## 已知事實（文件推導，待實測）

- Hermes 的專案 context 在 session 開始載入；改磁碟檔不會替換已載入的規則（`G3` 的依據）。
- Hermes 子代理不能 `clarify`；提問只能由頂層 session 發出。
- Hermes 掃 skill 目錄用 `os.walk(followlinks=True)`，symlink 理論上可被發現；仍需實測。
